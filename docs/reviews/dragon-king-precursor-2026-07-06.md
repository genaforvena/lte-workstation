# LITERATURE review — Dragon-King theory vs. our level-only pressure gates (2026-07-06)

**Area:** complex adaptive systems / edge of chaos (Santa Fe), from the angle of a *known critique / failure mode*.

## The critique (live, continuously published)

The Santa Fe paradigm — self-organized criticality (Bak), the "edge of chaos" (Langton/Packard),
scale-free power laws everywhere — carries an implicit fatalism about extremes: the biggest events
live in the far tail of a power law, are generated by the *same* dynamics as small events, and are
therefore essentially **unpredictable** ("black swans"). Didier Sornette's **Dragon-King theory** is a
direct, still-active (2009 → 2020s) critique of that view.

A **dragon king** is an extreme event that lies **outside** the fitted power-law tail — statistically
"impossible" under the scale-free assumption — because it is produced by a **different, endogenous
mechanism**: a transient increase in *coupling strength* between components creates a positive-feedback
loop → **super-exponential growth** → a bifurcation / phase transition into a qualitatively new state.
The payoff of the critique is the opposite of fatalism: because a dragon king is *maturing* through a
detectable precursor (super-exponential acceleration, log-periodic oscillation), it is **predictable and
sometimes suppressible** — unlike a genuine power-law black swan.

**Sources:**
- Sornette, D. (2009). *Dragon-Kings, Black Swans and the Prediction of Crises.* Int. J. Terraspace Sci.
  & Eng. — https://arxiv.org/abs/0907.4290 / SSRN https://doi.org/10.2139/ssrn.1596032
- Sornette, D. & Ouillon, G. (2012). *Dragon-kings: mechanisms, statistical methods and empirical
  evidence.* Eur. Phys. J. Special Topics 205. — https://arxiv.org/pdf/1205.1002
- Overview: https://en.wikipedia.org/wiki/Dragon_king_theory

## The concept we do NOT embody

Every extreme-event gate in the mesh is a **level** detector: it fires when a *snapshot* crosses a static
threshold. `mesh-resource-guard`'s `node_pressure_classify` (scripts/mesh-resource-guard:136) fires when
`MemAvailable < mem_pct%` **or** `SwapFree < swap_pct%` — a single-frame comparison, no memory of the
*trajectory*. `mesh-hw-fault-watch` debounces a fault *stream* (rate-limits repeats) but never measures
its acceleration. `mesh-heavy-run` (just built) gates on level headroom.

None of these embody the dragon-king insight: **the precursor is in the second derivative, not the
level.** The 20:05–20:12Z OOM batch-kill (~8 processes) and the 02:04Z 2.5GB-RSS python kill were not
random tail events — they were dragon kings born of endogenous coupling (unniced heavy jobs stacking →
swap-thrash → each allocation slows the box → more jobs pile up → super-exponential memory collapse). A
static level gate sees nothing until `MemAvailable` is already *below* the line — by which point the
trajectory is already accelerating *through* it, too late to defer the job that tips it over.

## Concrete application (one file)

**`scripts/mesh-resource-guard`** — add a **dragon-king precursor axis** alongside the level axis:

- Keep a tiny rolling sample of `MemAvailable` (last N passes, e.g. 5, in `$MESH/.rg-memhist`).
- Each pass, compute the **acceleration** of consumption (second difference of MemAvailable, or the
  ratio of successive drop rates). A **super-exponential** signature = consumption rate itself rising
  (drop_{t} > drop_{t-1} > drop_{t-2}) while headroom is still *above* the level line.
- Emit a new **`[node-accelerating]`** edge (distinct class, edge-gated like the existing node-pressure
  flag) *before* the level threshold trips.
- `mesh-heavy-run`'s `node_clear()` then consults this precursor too, so it **defers a heavy job on the
  super-exponential ramp**, not only once the cliff is reached — converting a "too late" refusal into a
  genuine early one, exactly the dragon-king prediction/suppression the theory prescribes.

This is a real gap: we react to the *state* of the tipping point; dragon-king theory says the actionable
signal is the *curvature of the approach*. Implementation-ready but deliberately left as a proposal —
adding an acceleration detector without a proper false-positive null-test would itself commit the sibling
sin the same literature warns about (asserting criticality without testing it), so it is filed for a
dedicated build+`--test` pass, not rushed into this review.

## UPDATE 2026-07-06 — BUILT (with the null-test the deferral demanded)

Shipped in a subsequent build baton, exactly as scoped above:

- **`scripts/mesh-resource-guard`** — pure `node_accel_classify()` decides a super-exponential ramp from
  a rolling MemAvailable series (last N passes in `$MESH/.rg-memhist`): fires only when the last 3 drops
  are all positive, *strictly increasing* (`d3>d2>d1`), and the latest exceeds a 150MB noise floor. New
  edge-gated `[node-accelerating]` class emitted in `--alert` (push+classify) and surfaced read-only in
  `--status`. Visibility only — never kills, same posture as DUAL-ELEVATED.
- **`scripts/mesh-heavy-run`** — `node_clear()` now greps `^NODE-(PRESSURE|ACCELERATING):`, so a heavy
  job DEFERS on the ramp, not only at the level cliff — the prediction→suppression the theory prescribes.
- **False-positive null-test** (the deferral's precondition): a 9-case battery asserts SILENT on steady
  drain, decelerating drain, freeing memory, oscillation, a lone late spike, a sub-floor ramp, too-few
  samples, and empty history — FIRE only on a genuine super-exponential ramp. Falsify-verified: weakening
  the strict-acceleration gate trips exactly the steady/decelerating/late-spike fixtures.

Left uncommitted for the steward to land.
